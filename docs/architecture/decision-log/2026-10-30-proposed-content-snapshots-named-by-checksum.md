# 2026-10-30

Proposed, not decided: give each published content snapshot a stable name, its SHA-256 checksum over a canonical serialization (RFC 8785, JSON Canonicalization Scheme) instead of `JSON.stringify`, and store that checksum, or the item's stable ID plus the checksum, wherever a saved pick names its content version, alongside the existing version number. Why: `published_content_versions.version` is a Postgres `serial` and saved picks reference it by foreign key, so a pick only has meaning inside this one database. A checksum that anyone can recompute from the content lets picks survive export, restores and mirrors, lets a client verify the snapshot it received, and stays stable if content is ever served from a cache or a second region. `JSON.stringify` depends on key order, so the same graph built two ways can hash differently today. Cheap before launch; a data migration once picks and measurement depend on the integer. Alternatives: keep the integer alone; switch to random snapshot IDs (portable, but not verifiable). No code changes with this record.
